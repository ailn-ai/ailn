# How payment works

The payment path. The paid call is currently closed by the pre-mint gate; this documents how it works when it opens.

---

## The flow

```
1. agent  GET  /mcp              discovery: what is for sale, current price
2. agent  POST call              server returns the price in a payment challenge
3. agent  sign authorization     offline, no transaction sent, no gas
4. agent  POST call + proof      server verifies settlement, returns data
```

Step 3 is the part wallets warn about. Signing an offline authorization that lets a server
pull a bounded amount is the same pattern phishing uses. The warning is correct behavior, not
a false positive, and it is inherent to x402.

**Use a dedicated small-balance wallet.** Check the amount cap and validity window before
confirming.

---

## One settlement standard, four chains

| Chain | Asset | Standard | Why |
| --- | --- | --- | --- |
| Base | USDC | EIP-3009 | Native Circle USDC |
| Arc | USDC | EIP-3009 | USDC is also the gas token |
| X Layer | USDC / USDT | EIP-3009 | |
| Arbitrum | USDC | EIP-3009 | |

**BNB Smart Chain is not a settlement chain.** Its USDC and USDT do not implement EIP-3009, so an
offline authorization cannot be settled there; BNB is used only for balance top-up. The challenge
is therefore delivered as **HTTP 200 with a `payment_required` error**, not a 402 status.

The four accepted deployments still differ in their EIP-712 domain (`name`, `version`), which is
the next section.

---

## The EIP-712 domain trap

Each token has its own EIP-712 domain. `name` and `version` differ across tokens, and **getting
either wrong makes every signature fail** — usually without a useful error message.

The four USDC/USDT deployments in use differ in both fields. Domain parameters here were
verified against each token's on-chain `DOMAIN_SEPARATOR()` rather than copied from
documentation.

If you are adding a chain: verify the domain on chain first. Documentation for these tokens is
inconsistent across deployments.

---

## Settlement is checked, not assumed

The server does **not** serve data because a signature verified. It serves data because
settlement was confirmed.

> A signature that verifies against an address with no funds is not payment.

This distinction is the whole security model. Any implementation that credits an account on
signature alone has a defect.

---

## What this does not cover

- **No refunds.** Settlement is final.
- **No credit.** You cannot pay later.
- **No subscription.** Every call is priced individually.
- **No fiat.** On-chain assets only.
- **Not Amber.** Amber is a `PROPOSED` protocol that would standardize this. What exists is an
  implementation; Amber is a specification. Do not confuse them.

## Pricing

Prices are quoted live per call. This repository does not hardcode them.

If you see a price in a document that disagrees with the endpoint, the endpoint is correct and
the document is stale. Report it.
